## Prompt Summary

Security review of the self-hosted app (lda.lemmata.app) found that DOCX, ODT and EPUB uploads are ZIP containers and the 50 MB upload cap only bounds the compressed size. A local experiment with the unchanged `read_file()` showed a 0.30 MB DOCX expanding to 90 MB of XML, peaking at about 1.5 GB RAM and 47 s of CPU while parsing. Because Streamlit re-runs the script on every widget interaction and `read_files()` was not cached, the same upload was re-parsed on each interaction.

Fix it locally (not deployed): reject archives whose uncompressed size is too large before parsing, and cache parsing results.

## Response Summary

- `config.py`: added `ARCHIVE_EXTENSIONS`, `MAX_ARCHIVE_UNCOMPRESSED_MB = 200`, `MAX_ARCHIVE_MARKUP_MB = 40`. These values are a technical proposal (not from literature); markup (XML/HTML) gets the tighter cap because it drives parser memory.
- `file_io.py`: new `_check_archive_size()` reads the ZIP central directory and rejects archives above either cap with a user-facing `FileReadError`, before any XML is parsed. Called from `read_file()` for docx/odt/epub.
- `app.py`: `_read_files_cached()` wraps `read_files()` with `st.cache_data(max_entries=8, ttl=3600)` keyed on (filename, bytes), so uploads are parsed once instead of on every rerun.
- `tests/test_file_io.py`: `TestArchiveGuard`, covering a normal DOCX, a bomb DOCX, a DOCX with understated sizes in its headers, and a corrupt archive.

## Decision

No methodological change. Text extraction output is unchanged for files under the caps.
